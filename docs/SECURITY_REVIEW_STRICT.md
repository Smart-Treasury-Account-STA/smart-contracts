# Strict Security Review: Design and Code

**Scope:** every contract in this workspace (`smart_account`, `recovery_manager`, `policy_engine`, `intent_registry`, `transfer_adapter`, `split_adapter`, `webauthn_verifier`, `governance_account`, `threshold_policy`, and `account_factory`, added this cycle) and the design documents that describe them, principally `docs/GOVERNANCE_MULTISIG_DESIGN.md`. This is a follow-up to the review rounds already recorded in `docs/V1_SCOPE.md` §4–§6 — it does not repeat their findings, only what surfaced beyond them.

**Method:** every entrypoint's authorization gate was re-derived from source (this contract's own code, and the OZ crate source it composes — never from memory or from what a doc comment claimed), cross-checked against `docs/TECHNICAL_ARCHITECTURE.md`'s stated invariants, and checked for: replay/state-consumption bugs, TTL/storage-archival coverage, arithmetic overflow, error-code collisions, and whether a design document's description of *what a change protects* matches what the code actually gates. A later pass added: whether every documented user workflow (`docs/TECHNICAL_ARCHITECTURE.md` §12) is actually reachable end to end from a fresh deployment, and whether "deploy and configure a treasury" is realistically something a user — not just this project's own team — can do.

## 1. Stale guardian-freeze flag allowed unauthorized re-freeze (Fixed)

**Finding.** `recovery_manager::request_guardian_freeze` set a persistent boolean flag (`GuardianFreezeRequested`). `smart_account::apply_guardian_freeze` read it via `guardian_freeze_requested()` — a plain view, never cleared. Once any guardian had ever requested a freeze, the flag stayed `true` forever. Contrast with the recovery path's own `AppliedRecovery` flag, which *is* consumed. Practical effect: `apply_guardian_freeze` could be called an unbounded number of times after a single freeze request, including long after the incident that prompted it was resolved and the treasury unfrozen again by the owner — re-freezing the treasury required no fresh guardian action at all.

**Fix.** Added `recovery_manager::consume_guardian_freeze_request`, which reads the flag and clears it in the same call:

```rust
pub fn consume_guardian_freeze_request(env: Env) -> bool {
    let key = DataKey::GuardianFreezeRequested;
    let requested = env.storage().persistent().get(&key).unwrap_or(false);
    if requested {
        env.storage().persistent().remove(&key);
    }
    requested
}
```

`smart_account::apply_guardian_freeze` now calls this instead of the old read-only view. See `contracts/recovery_manager/src/lib.rs` (`consume_guardian_freeze_request_clears_it_exactly_once`, `consume_guardian_freeze_request_with_nothing_pending_returns_false`) and `contracts/smart_account/src/test.rs` (`apply_guardian_freeze_cannot_replay_an_already_consumed_request`, which proves a second `apply_guardian_freeze()` call with no intervening `request_guardian_freeze` now fails with `Error(Contract, #8012)`).

## 2. `transfer_adapter` / `split_adapter` had no permissionless TTL maintenance (Fixed)

**Finding.** `docs/TECHNICAL_ARCHITECTURE.md` §16 requires every contract to expose a permissionless way to extend its own instance TTL, independent of its main business logic succeeding — because Soroban instance-storage archival is not a soft failure: an archived contract cannot be invoked at all without a separate restore operation. Every other contract in the workspace already had this (`smart_account::extend_instance_ttl`, `recovery_manager::extend_ttl`, `policy_engine`, `intent_registry::extend_intent_ttl`, `governance_account::extend_instance_ttl`). `transfer_adapter` and `split_adapter` did not: their only TTL-touching code path was inside `execute_transfer`/`execute_split`, both of which require the configured treasury's own authorization to even reach. A treasury that goes fully dormant — plausible for e.g. a quarterly-disbursement treasury that only ever calls `execute_transfer` and never `execute_split`, or vice versa — had no way for *anyone* to keep the untouched adapter's instance storage alive.

**Fix.** Added `extend_instance_ttl(env: Env)` to both contracts, matching the exact shape already used elsewhere in the workspace. See `contracts/transfer_adapter/src/lib.rs` / `src/test.rs` (`extend_instance_ttl_is_permissionless`) and `contracts/split_adapter/src/lib.rs` / `src/test.rs` (same test name).

## 3. Cross-contract numeric error-code overlap with OZ's own ranges (Informational, no fix)

**Finding.** This workspace's own contracts are each assigned a disjoint 1000-wide error-code block (`policy_engine` 2000s, `intent_registry` 3000s, `recovery_manager` 4000s, `webauthn_verifier` 5000s, `transfer_adapter` 6000s, `split_adapter` 7000s, `smart_account` 8000s, `governance_account` 9000s — verified by reading every `#[contracterror]` enum directly, no collisions among them). However, `intent_registry`'s 3000s block collides numerically with OZ's own `stellar_accounts::smart_account::SmartAccountError`, which also starts at 3000 (`ContextRuleNotFound = 3000`, `UnvalidatedContext = 3002`, …) — confirmed directly against `stellar-accounts-0.7.2/src/smart_account/mod.rs`. For example, a bare `Error(Contract, #3002)` diagnostic means `IntentAlreadyExists` if it came from `intent_registry`, but `UnvalidatedContext` if it came from `smart_account`'s own `__check_auth`.

**Why this is not a bug:** Soroban scopes errors by which contract's invocation actually failed — a `simulateTransaction`/`getTransaction` result always identifies the failing contract address alongside the raw code, so no client correctly reading the full diagnostic can actually confuse the two. It is only a risk for a human skimming a bare error number out of context (e.g. copy-pasted into a support message without the contract address). No code change is warranted; noted here so it isn't mistaken for an unreviewed gap.

## 4. Governance design does not protect signer/context-rule/policy administration (documented, not code-fixed)

**Finding.** `docs/GOVERNANCE_MULTISIG_DESIGN.md`'s original §1 stated that `add_context_rule`/`add_signer` were among `smart_account`'s "owner-gated calls." This was checked directly against the OZ crate source rather than taken on faith, and it is incorrect: `add_context_rule`, `update_context_rule_name`, `update_context_rule_valid_until`, `remove_context_rule`, `add_signer`, `remove_signer`, `add_policy`, and `remove_policy` are all OZ trait defaults gated by `e.current_contract_address().require_auth()` (`smart_account`'s own composed signer/context-rule system), not by the separate `owner` field:

```rust
// stellar-accounts-0.7.2/src/smart_account/mod.rs
fn add_signer(e: &Env, context_rule_id: u32, signer: Signer) -> u32 {
    e.current_contract_address().require_auth();
    storage::add_signer(e, context_rule_id, &signer)
}
```

**Why this matters.** The entire point of `docs/GOVERNANCE_MULTISIG_DESIGN.md` is to repoint `owner` at a multisig (`governance_account`) so a single compromised key can no longer unilaterally control the treasury. That protects `propose_adapter_change`, `freeze`, `pause`/`unpause`, and `transfer_ownership` — but it does **not** protect the eight calls above. Concretely: today, whoever satisfies any one context rule (e.g. rule 0's sole signer) can add new signers to that rule, remove existing ones, attach or detach policies, or create an entirely new context rule granting themselves broader authority — with zero owner or governance involvement. Deploying `governance_account` and repointing `owner` at it, exactly as this design document recommends, would do nothing to close this. A single compromised payment-signer key is effectively a compromise of the treasury's entire authorization topology, not just that one rule's spending power.

**Considered fix (not applied).** The same override pattern `smart_account` already uses for `pause`/`unpause` (add an `ownable::enforce_owner_auth(e)` check on top of the OZ default) would close this cleanly for all eight calls — verified the underlying `storage::add_signer`/`storage::add_context_rule`/etc. free functions are all `pub`, so the override is mechanically straightforward. **This was deliberately not implemented in this pass.** It is a breaking change to every already-integrated caller of these eight entrypoints — `scripts/add_dev_test_signer.py`, `scripts/swap_context_rule_signer.py`, `scripts/dev_fix_rule_signers.py`, `scripts/set_intent_executor.py`, and any equivalent dApp code — each of which would need to add a second, owner-scoped authorization entry to its transaction construction. That directly conflicts with this project's standing priority that dApp integration stay easy, not accumulate complexity. Silently shipping a breaking auth change to a live, externally-integrated testnet deployment without coordinating it first is a worse outcome than leaving a named, documented gap.

**Disposition.** Recorded as new §9 in `docs/GOVERNANCE_MULTISIG_DESIGN.md`, "Known limitation: this design does not protect signer/context-rule/policy administration," with the same operational-mitigation framing already used for `governance_account`'s own no-recovery-path gap (§7): treat any context rule's signer set as equivalent in sensitivity to full topology control, because in practice it is. The fix remains fully scoped for whenever it's coordinated with the dApp: add the same `ownable::enforce_owner_auth` override used by `pause`/`unpause` to all eight calls, updating every listed caller in the same change.

## 5. No self-service way to deploy and configure a treasury (Fixed)

**Finding.** `docs/TECHNICAL_ARCHITECTURE.md` §12.1 documents "Create a Smart Treasury Account" as a user workflow. In practice, standing one up meant seven separate contract deployments plus ten-plus ordered `stellar contract invoke` calls (`scripts/deploy_testnet.sh`), including a Python script hand-constructing a raw Soroban authorization entry (§6 below). That is workable for this project's own testnet, not something a new user could realistically do. `docs/SMART_ACCOUNT_IMPROVEMENT_PROPOSAL.md` had already named this as "Priority 2 — Self-service deployment," flagging one real fork in the design: a factory could deploy a full private stack per treasury (simple, more expensive) or a shared multi-tenant `policy_engine`/`intent_registry`/`recovery_manager` (cheaper at scale, requires redesigning three already-shipped contracts' storage keys).

**Fix.** Added `contracts/account_factory`. `deploy_account(caller, salt, initial_signers, initial_policies, guardian_threshold, executor)` deploys fresh `policy_engine`, `intent_registry`, `recovery_manager`, `transfer_adapter`, and `split_adapter` instances via `env.deployer().deploy_v2`, wires them together, and returns a ready-to-use `smart_account` — one call instead of ten-plus. Deliberately takes the "private stack per treasury" fork, not the multi-tenant one: it requires zero changes to any already-shipped contract, and the multi-tenant question remains open for a dedicated future decision (see the contract's own module doc comment and `docs/SMART_ACCOUNT_IMPROVEMENT_PROPOSAL.md` Priority 2). `webauthn_verifier` is not redeployed — it is stateless, and this workspace already treats one shared instance as correct.

Verified with a real end-to-end test (`deploy_account_wires_a_fully_usable_treasury_in_one_call`, `contracts/account_factory/src/test.rs`) that deploys against **actual compiled WASM** (fixtures built via `stellar contract build --optimize`, committed under `contracts/account_factory/src/wasm_fixtures/`, not a mock) and executes a real SAC transfer through the freshly deployed stack in the same test.

## 6. `intent_registry` bootstrap was impossible for any external caller to produce (Fixed)

**Finding.** `intent_registry`'s `admin` must be `smart_account` itself (`create_intent`/`cancel_intent` are only ever called by `smart_account`, `ensure_admin`-gated on the `intent_registry` side). Calling `intent_registry.initialize(admin=smart_account_address)` from *outside* — a plain deployer keypair, or (the blocking problem for finding #5) a factory contract — requires `smart_account_address.require_auth()`, which the Soroban host can only satisfy via that treasury's own `__check_auth`, i.e. a real signed `AuthPayload` from its registered signers. At the moment this bootstrap needs to happen, no signers are registered yet. This project's own testnet deployment worked around it with `scripts/bootstrap_intent_registry.py`, hand-constructing the raw authorization entries directly against XDR types — a real, working, but entirely bespoke solution unavailable to a smart contract (a factory has no way to run a Python script mid-transaction), and a genuine blocker for finding #5.

**Fix.** `smart_account::initialize` now calls `IntentRegistryClient::new(&env, &intent_registry).initialize(&env.current_contract_address())` directly, as part of its own body. This is not the same call from a different location — it changes *who the direct caller is*. Soroban's invoker-shortcut means a contract's own `require_auth()` on *its own address* needs no signature at all when it is the direct caller making that exact call; `smart_account` calling `intent_registry.initialize` with itself as `admin` is exactly that case. Calling it from outside is not, because the intermediate caller (a deployer key, or a factory contract) is not `smart_account`.

This was not assumed — it was verified with a real, precise `mock_auths` test rather than the workspace's usual blanket `mock_all_auths()` (which auto-satisfies every `require_auth()` regardless of whether the shortcut genuinely applies, so it cannot distinguish a real fix from a coincidentally-passing one). `initialize_bootstraps_intent_registry_with_no_separate_authorization` (`contracts/smart_account/src/test.rs`) authorizes *only* the top-level `initialize` call, with an empty `sub_invokes` list — no separate auth entry for `intent_registry` at all — and confirms the call still succeeds, then separately confirms `intent_registry` is genuinely initialized (a second `initialize` call against it fails).

`scripts/bootstrap_intent_registry.py` and the historical record in `docs/TESTNET_DEPLOYMENT.md` §6.3 remain accurate for the *existing* testnet deployment, which was bootstrapped the old way before this fix existed; both are now marked as no longer needed for new deployments.

## 7. New treasuries had no working adapter for a day (Fixed)

**Finding.** `smart_account::initialize` never accepted adapter addresses; binding one required `propose_adapter_change` followed by `apply_adapter_change` roughly 17280 ledgers (~1 day) later — a deliberate, previously-reviewed fix (`docs/V1_SCOPE.md` §6) protecting an *already-funded, already-operating* treasury from having its execution routing silently swapped out from under it. Applied uniformly, that same delay also gated a treasury's *first-ever* adapter binding, meaning a freshly created account (via the factory, or the manual script) could not execute a single payment for a full day after creation, for a risk (bait-and-switching an established binding) that does not exist yet on an account with zero prior configuration and no funds.

**Fix.** Added `initial_adapters: Map<Symbol, Address>` to `smart_account::initialize` (folded into the new `InitConfig` struct — see §"Argument count" below), setting `DataKey::Adapter(operation)` directly with no timelock. Every *later* rebinding is untouched and still goes through the timelock. Verified with `initial_adapters_are_usable_immediately_with_no_timelock` (`contracts/smart_account/src/test.rs`): a real SAC transfer executes successfully on the same ledger `initialize` ran on, with no `apply_adapter_change` call or ledger advance anywhere in the test.

## 8. `intent_registry`'s default `Executor` silently defeats the relayer gate (Fixed)

**Finding.** `intent_registry::initialize(admin)` defaults `Executor` to `admin`. After the fix in §6, `admin` is `smart_account`'s own address. `execute_scheduled_payment`'s doc comment claims "an operational relayer key … gates *when* within the valid window execution happens," enforced by `intent_registry.mark_child_executed`'s `executor.require_auth()`. But `execute_scheduled_payment` itself has no `require_auth()` of its own (deliberately — see that function's doc comment), and its nested call into `mark_child_executed` is made by `smart_account`, which is *also* the default `Executor`. By the same invoker-shortcut mechanism that correctly fixes §6, that nested check would be satisfied for free regardless of who called `execute_scheduled_payment` in the first place — silently making it callable by anyone, not gated by any relayer identity at all, contradicting the documented property. (This does not create a fund-safety issue by itself — every value used is still pinned to the canonical intent, per the existing fix recorded in `docs/V1_SCOPE.md` §4 — but it does mean the "operational" throttle the design describes doesn't exist until a caller notices and fixes it.)

**Fix.** Added `initial_executor: Address` to `smart_account::initialize`, which now calls `intent_registry.set_executor(&initial_executor)` immediately after `intent_registry.initialize(...)`, using the same invoker-shortcut. This forces a deliberate choice at creation time rather than an accidental default; passing the treasury's own address again is still possible and valid (for a deployer who genuinely wants anyone to be able to trigger execution), but it is now a choice, not a side effect of `IntentRegistry`'s generic `initialize(admin)` shape.

Verified with `execute_scheduled_payment_without_executor_authorization_fails` (`contracts/smart_account/src/test.rs`): with an explicit, distinct `initial_executor`, a call with **no** mocked or real authorization at all (`env.set_auths(&[])`) correctly panics — proving the gate is real, not merely present in a doc comment.

## 9. `policy_engine`'s admin was silently missing from the governance-distribution plan (Fixed)

**Finding.** Surfaced while reviewing roles for `docs/TECHNICAL_ARCHITECTURE.md` §12.8 (the new complete role/transaction reference — see below). `docs/GOVERNANCE_MULTISIG_DESIGN.md`'s opening status line claims `governance_account` is "ready to deploy as... the `admin` of `recovery_manager`/`policy_engine`," but §1 ("Problem, precisely stated") and §8 ("Next step") — the sections that actually define the plan — only ever mention `recovery_manager`'s admin. Following §8's "next step" literally would leave `policy_engine`'s admin (`set_asset_rule`, `set_recipient_allowed`, `set_operation_allowed`, `bump_version`) on a bare single keypair even after "distributing the admin/owner role" was declared done, contradicting the document's own opening claim.

**Why this isn't a deliberate scope boundary.** `policy_engine::ensure_admin` is the identical `admin.require_auth()` shape as `recovery_manager`'s — pointing `governance_account` at it costs nothing extra and needs no code change, exactly matching this design's own stated premise ("distributing the owner/admin role does not require touching `contracts/smart_account` or `contracts/recovery_manager` at all," §2). There was no reasoning anywhere in the document for treating it differently; it read as an incomplete enumeration, not a decision.

**Fix.** §1 and §8 of `docs/GOVERNANCE_MULTISIG_DESIGN.md` now include `policy_engine`'s admin alongside `recovery_manager`'s throughout, with a note explaining the correction. `docs/TECHNICAL_ARCHITECTURE.md` §12.8's own "distributing the owner role" paragraph was written consistent with the corrected version from the start.

## Argument count: `InitConfig` / `SmartAccountInitConfig`

Adding `initial_adapters` and `initial_executor` pushed `smart_account::initialize` to 9 parameters, past `clippy::too_many_arguments`'s default limit of 7 — caught by this project's own `-D warnings` CI gate, not silently allowed through. Rather than suppress the lint, the five subordinate-module-wiring parameters (`policy_engine`, `intent_registry`, `recovery_manager`, `initial_adapters`, `initial_executor`) were grouped into a new `InitConfig` struct, bringing `initialize` down to 4 real parameters plus `env`. `contracts/account_factory` mirrors this locally as `SmartAccountInitConfig` (same field names/types — Soroban struct types are decoded structurally, so this needs no crate dependency, matching the rest of that module's client-declaration pattern) rather than depending on `sta-smart-account` directly.

## Re-review of the fixes themselves

Each fix above was re-read after landing, specifically looking for problems the fix itself could have introduced:

- **Finding 1's fix** (`consume_guardian_freeze_request`): confirmed it uses `persistent().remove`, not just overwriting with `false` — so no stale-key TTL bookkeeping is left behind. Confirmed the *only* caller of the old `guardian_freeze_requested` view was `smart_account::apply_guardian_freeze`, so removing the view and replacing it with the consuming version has no other call site to miss. Confirmed the new test asserts the *second* call's `Error(Contract, #8012)` specifically — that's `smart_account`'s existing "nothing to apply" error, i.e. the fix causes a *second* `apply_guardian_freeze` to fail for the same reason a *first* one would fail with no request ever made, not a new or different error path.
- **Finding 2's fix** (`extend_instance_ttl` on both adapters): confirmed the function is a plain, unauthenticated read-free write to instance TTL only — it cannot be used to move funds, change the configured treasury address, or read/write any other state, matching every other contract's identically-shaped maintenance entrypoint. Confirmed via `extend_instance_ttl_is_permissionless` (`e.set_auths(&[])` before calling) that no authorization is accidentally required.
- **Finding 4's documentation fix**: re-read `docs/GOVERNANCE_MULTISIG_DESIGN.md` §1 and the new §9 together to confirm they no longer contradict each other, and confirmed the corrected §1 wording still accurately lists the calls that genuinely *are* owner-gated (`propose_adapter_change`, `freeze`, `pause`/`unpause`, `transfer_ownership`) without dropping any of them.
- **Finding 5's fix** (`account_factory`): re-read `deploy_account` specifically checking for salt reuse/collision handling (`deploy_account_with_a_reused_salt_for_the_same_caller_fails` confirms a second deployment under the same salt traps rather than silently overwriting anything — Soroban's own `create_contract_with_constructor` rejects the collision), and for whether any deployed sub-contract address could leak into the wrong treasury's wiring (traced every address from its own `deploy(...)` call through to exactly one `initialize` call, no address is reused across two different roles). **Caught a real doc-comment overclaim on this re-review**, not in the earlier draft: the module doc originally said `caller.require_auth()` is needed "exactly once, for the whole batch" and that "one signature … cover[s] every node" — inaccurate. `caller.require_auth()` actually fires six times (once directly, five times nested inside each sub-contract's own `initialize`), each needing its own authorization entry; it just doesn't have `intent_registry`'s specific chicken-and-egg problem, since `caller` is a real, already-existing address a wallet can sign for six times in one flow. Corrected in the doc comment.
- **Finding 6's fix** (`intent_registry` self-bootstrap): the risk with this class of fix is claiming a shortcut applies when it doesn't and shipping a call that would actually panic on real (non-mocked) testnet. Addressed by writing `initialize_bootstraps_intent_registry_with_no_separate_authorization` with a genuinely precise `mock_auths` list (empty `sub_invokes`) rather than trusting the reasoning alone — this is real, if partial, evidence the shortcut holds, closer to proof than the doc-comment claim in finding 5 above got without a matching test. Also confirmed `intent_registry` staying uninitialized between `env.register(...)` and `smart_account::initialize` (both in `account_factory::deploy_account` and `scripts/deploy_testnet.sh`) is safe: nothing else touches it in between.
- **Finding 7's fix** (`initial_adapters`): confirmed the no-timelock path only ever runs inside `initialize` itself, gated behind the same `AlreadyInitialized` check and `owner.require_auth()` as everything else in that function — there is no way to reach this code path a second time on an already-initialized (and therefore possibly funded) treasury to smuggle in a fast, untimelocked adapter swap later.
- **Finding 8's fix** (`initial_executor`): confirmed `set_executor` is called *after* `intent_registry.initialize` in program order (a call to `set_executor` before the registry is initialized would fail `ensure_admin`'s lookup), and confirmed the fix doesn't change behavior for the *already-deployed* testnet `intent_registry`, whose `Executor` was already explicitly set to a real relayer address independently of this fix (`docs/TESTNET_DEPLOYMENT.md`).

No new issues were introduced by any of the fixes in this pass, beyond the one doc-comment overclaim caught and corrected during this same re-review (finding 5).
